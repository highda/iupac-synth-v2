# Dependencies and canonical environment

The canonical build and test platform is Debian 12 (bookworm) on linux/arm64; macOS arm64 is the second native target. This document pins the third-party inputs, describes the development environment and fixes the self-contained delivery contract. Verification gates are in [VERIFICATION.md](VERIFICATION.md).

## Development environment

Linux development happens in a Debian 12 arm64 container (Apple Silicon host with Docker Desktop, or any arm64 Linux host): four CPUs, 8 GiB RAM, 1 GiB shared memory, at most four parallel build jobs (two for the validator under memory pressure), no privileged or host-network mode.

Keep ALSA/JACK dev libraries for Standalone, X11/Xrandr/Xinerama/Xcursor/Xext, FreeType, GL, Xvfb and xauth for headless editor/validator. No GTK/WebKit development libraries: native JUCE GUI uses no WebView. Add Python RDKit/NumPy, Python venv/pip packaging tools, OpenJDK 17 JDK (including jlink/jdeps), and shellcheck. These are developer tools, never end-user installation steps. Do not embed download/bootstrap logic in the plugin. Caches may be cleared independently; never use a cache as the only copy of a required input.

Native macOS arm64 work needs the Xcode Command Line Tools, CMake, Ninja, jq and shellcheck, plus Homebrew `python@3.11` and `openjdk@17` (with jmods, for jlink/jdeps) for the chemistry payload; [BUILDING.md](../BUILDING.md#native-macos-arm64) lists the exact steps. AU validation (`auval`, pluginval on the `.component`) needs a console login session with a live `AudioComponentRegistrar`.

## Build and delivery contract

CMake presets `linux-synth` (chemistry OFF), `linux-chemistry`, `linux-release` (full product), `linux-sanitize` (ASan+UBSan) and `linux-tsan` build into matching `build/` directories; `mac-synth` and `mac-release` are their Darwin counterparts. V0 uses `linux-synth`; final verification retains it alongside the full build. Release gate commands:

```sh
cmake --preset linux-release
cmake --build --preset linux-release --parallel 4
ctest --preset linux-release --output-on-failure
./scripts/verify-release.sh
```

`verify-release.sh` runs the V0–V11 production-path checks and write reports under `out/verification/<commit>/`. Sanitizers: ASan+UBSan build and separate TSan coordinator test, not ASan+TSan together. Benchmark the release build without instrumentation. Xvfb pluginval strictness 5 is required; configure no-audio-device GUI smoke as appropriate. Do not silently skip test categories because a dependency was not installed.

Install stages the complete product into an explicit prefix and never runs as a side effect of build. Plugin identity differs from v1: product `IUPAC Synth 2`, manufacturer code `Iups`, plugin code `Iup2`, bundle ID `space.highda.iupacsynth2`; state cannot collide with `Iup1`. Linux formats VST3/Standalone; CMake adds AU only on Apple. Each delivered plugin/app package includes the licensed offline discovery snapshot/index and factory patches, the frozen helper, its private runtimes, OPSIN JAR and required notices. CLI distribution includes the same payload. There is no separate Python/Java/RDKit prerequisite, interpreter selector, Docker requirement or first-run download for users.

## Self-contained runtime package

This is a hard end-user invariant. Self-contained means one complete installation with internal executables/resources; it does not require placing a JVM or Python interpreter inside the audio process or compiling everything into one binary.

- **Python/RDKit:** freeze the exact production helper with PyInstaller 6.22.3 in `onedir` mode, including the Python interpreter, required modules, RDKit data, and native library closure (including Boost/NumPy dependencies actually loaded). Maintain one small checked-in spec/hook configuration and dependency/license inventory. Do not assume automatic import analysis collects every RDKit library/data file. No per-launch extraction into temporary executable directories.
- **OPSIN/Java:** bundle the pinned JAR and a private, relocatable OpenJDK 17 runtime image produced from a pinned target-native JDK using jlink. Use jdeps plus the actual name/stereo/error panels to select a sufficient module closure; retaining the full module set is an acceptable fallback, not a required permanent layout. Avoid a runtime-minimization research project. Retain relevant JDK notices/source-compliance material. Always invoke the shipped Java executable by an absolute bundle-relative path.
- **Placement:** on macOS put one complete private payload — frozen helper, its native closure, the private Java runtime, OPSIN, the discovery snapshot and notices — under each VST3/AU/app bundle's `Contents/Resources/chemistry`, and re-seal the bundle after staging. A nested-code location (`Contents/Helpers`, `Contents/Frameworks`) is the conventional home for a helper *bundle*, but `codesign` applies nested-code rules to everything it finds there and refuses a frozen PyInstaller/jlink tree outright (`bundle format unrecognized, invalid, or unsuitable` at `_internal/numpy/.dylibs`; `code object is not signed at all` at `java/lib/jvm.cfg`), whereas the resources layout signs and passes `codesign --verify --strict` — which is what "package layout must permit native signing later" has to mean. The payload declares its own artifact paths in `helper/payload-layout.json`, so resolution never depends on a case-insensitive filesystem folding `resources` onto `Resources`. Linux VST3 resources and the Standalone/CLI distribution directory contain the same complete private payload. Each installable format works when installed alone; do not require another format or the source checkout. Duplicating a payload across formats is acceptable; a shared runtime installer/service is unnecessary. Resolve paths from the loaded plugin module/application location, not the host DAW executable or working directory.
- **Isolation:** the plugin spawns the frozen helper; only that child runs Python and Java. No interpreter/JVM in the host audio process. Preserve shell-free arguments, cancellation/deadlines and generation rules. Sanitize Python/Java and dynamic-loader environment settings inherited from the DAW; when the frozen helper launches Java, use its private runtime's library paths rather than blindly inheriting the freezer's search path. Do not modify the DAW process environment globally. Upstream documents [subprocess library-search pitfalls](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html).
- **Portability:** build/freeze each payload natively for its target OS/architecture. Linux arm64 packaging does not prove macOS packaging. OS kernel/system-framework baseline dependencies are allowed and enumerated; language runtimes and non-system chemistry libraries must ship. Pin the canonical backend/version and verify identical analysis from unfrozen and frozen forms. On other targets an unavailable backend build is an explicit platform packaging blocker, never permission to tell end users to install Python/Java.
- **Relocation/integrity:** test moving the complete package to a path containing spaces, with a read-only installation directory and writable user temp/cache. Preserve internal relative symlinks and executable permissions; no symlinks may escape the package into a developer environment. No absolute Homebrew, venv, JDK, build or source paths. Bundle doctor verifies the private payload and reports repair/reinstall on damage. Missing-helper preset playback is a recovery case, not proof of complete delivery.
- **Evidence:** the helper packaging stage proves analysis parity and clean-machine operation; final V10 repeats this through installed plugin/CLI production paths. Record compressed/unpacked package size, native dependencies and startup timing; no arbitrary size optimization or module-pruning project is required. Signing/notarization remain outside this release, but package layout must permit native signing later.

A clean-machine gate must execute the shipped helper and installed plugin/CLI on the canonical OS without Python, Java, RDKit, Homebrew/Conda/venv tooling or the source tree installed/mounted, and with networking disabled. Use a separate minimal runtime test container, not merely a stripped PATH inside the fully provisioned development container. Test an OPSIN-supported IUPAC name absent from the alias table and valid unseen SMILES, then run the maintained panels, render, save and restore. Assert real resolved analysis/provenance; factory presets or helper-disabled playback cannot pass this gate. Cold startup must meet the existing helper deadline. Build tools remain exclusively in the development image.

PyInstaller's [documented bundle model](https://pyinstaller.org/en/stable/operating-mode.html) includes the interpreter but requires target-native builds and explicit missing-data/library collection. Its [license exception](https://pyinstaller.org/en/stable/license.html) covers generated bundles subject to dependency licenses. OpenJDK's [jlink](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jlink.html) creates private runtime images. These sources establish packaging mechanisms; actual RDKit/OPSIN payload completeness is established by the packaging tests.

## Runtime-only test orchestration

Packaging layout/hooks, native runtime module closure and equivalent self-contained directory packaging are implementation choices; document any changed mechanism and prove identical installed behavior.

Product packaging validation runs in a repository GitHub Actions job on `ubuntu-24.04-arm`, triggered only by pull requests that touch source or packaging paths, or dispatched by hand for release verification, using Docker to build the pinned Debian 12 product inputs and execute the separate minimal Debian 12 runtime image with `--network none`. The Ubuntu VM is orchestration only; the tested product OS/architecture remains Debian 12 arm64. Pin action commits and container digests, record runner identity and artifact hashes, retain workflow reports, and match tested artifacts to delivery.

Use product-only multi-stage build/runtime Dockerfiles, not a development container, as the release image. Build inputs come from the product lock and recorded Debian package revisions; retain/archive required inputs. Runtime stage includes only enumerated OS/UI/audio libraries, Xvfb/test launch support and the staged payload, no compilers, Python/Java/RDKit outside that payload, source mounts or network. Negative probes establish isolation before real analysis/plugin/CLI tests. A stripped PATH in a development image is insufficient. An unavailable CI runner is a blocker for the gate, never a reason to weaken V10 or claim completion without evidence.
